## 为什么需要通用方案

GLM-5.3-Flash 的官方 Jinja 模板会按 assistant 的工具调用顺序，通过调用 ID 查找并渲染工具结果；收到结果的顺序可能不同。模板负责生成图片占位符，但 LMDeploy 另行收集图片并提取特征。如果两条路径的顺序不同，图片会对应到错误的工具结果。

当前有限方案在渲染和收集前统一整理消息顺序，需要知道模型的模板规则。通用方案希望直接从最终渲染输出得到图片引用顺序，避免每支持一种重排模板就增加架构判断。

## 原型实现

1. `lmdeploy/vl/media_order.py` 为已解析的 image/video/audio 内容块分配输入索引，并复制相关消息字典，避免修改调用者输入。
2. `render_with_media_order()` 先用原有 `tokenizer.apply_chat_template()` 获得基准 prompt，再用经过 AST 修改的同一模板进行追踪渲染。
3. `_TrackMediaLoops` 给 Jinja 的 `For` 循环体前后插入请求独有的引用标记。只有循环变量确实指向媒体块时才输出标记。编译结果可缓存，引用表及标记前缀属于单次请求。
4. 在最终输出中读取成对标记，得到媒体输出顺序和每个引用包围的字符串；去掉标记后必须与基准 prompt 完全一致。漏图、重复图、不完整引用或输出变化会抛错，不会猜测输入顺序。
5. `MultimodalPrompt` 是携带 `media_order`、`media_contents` 的字符串子类。下游仍可读取普通 prompt，媒体收集器则根据索引重排图片及参数，并检查引用中的实际占位符。
6. `VisionModel.preprocess()` 和 `GLM5NextVisionModel.preprocess()` 将 prompt 元数据传入收集器，然后才进行特征提取。InternVL 走独立的旧处理路径，保留用户/工具图片转换及消息元数据修复。

该机制能够处理若干循环、宏和捕获字符串的情况，但**没有实现完整的 Jinja 字符串来源追踪**。不能把“增加循环标记”等同于“知道任意模板的最终媒体顺序”。

## 已知问题及归因

| 问题                         | 原因及影响                                                                                                                  | 归因                                           |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Qwen3-Omni 官方模板          | 在循环里把媒体 token 累加到变量，循环外才输出；循环标记没有跟随字符串传播。图片、视频、音频模板探针均抛错，普通图片也受影响 | 通用原型新引入；旧版没有这些拒绝               |
| 直接索引、按整数索引循环     | 没有可识别的媒体对象循环变量，无法得到引用                                                                                  | 通用原型新引入                                 |
| 宏结果 `.strip()`            | 插入的标记可能改变字符串边界与裁剪行为，导致输出或引用校验失败                                                              | 通用原型新引入                                 |
| `break` / `continue`         | 循环体末尾的结束标记可能不执行，留下不完整引用                                                                              | 通用原型新引入                                 |
| 自定义模型收集器             | 只接收消息、忽略 `MultimodalPrompt` 的路径不会自动采用输出顺序；存在模板/收集器适配缺口                                     | 原有扩展机制限制，不能靠前端追踪宣称解决       |
| MiniCPM 等旧处理路径         | 部分实现只处理 user 图片或有空内容限制；不同版本可能改变报错形态                                                            | 原有能力限制，不能一概归因于此次追踪           |
| Qwen3-VL-2B 工具任务回答错误 | 先前真实 GPU 对照中，基线也出现工具图片答案错误；HTTP 200 和模板正确不等于模型回答正确                                      | 不是已经证明由本次追踪引入的问题，根因尚未确认 |

历史前端审计中，Qwen3-Omni 有 25 个原先通过的组合变成失败；五类自定义模板在三协议下合计 15 个原先通过的组合变成失败。这些数字属于模板/前端诊断，不是 GPU 推理失败率。

`continue_final_message` 和 assistant token mask 暂未支持。实现还依赖 Transformers 的私有模板编译接口，需要评估版本兼容性。字符串被切片、替换、序列化或传递给自定义处理器时，也必须确保引用元数据没有丢失或过期。

## 可复现测试

安装仓库要求的依赖及 pytest 后，在本分支根目录运行：

```bash
python -m pytest tests/test_lmdeploy/serve tests/test_lmdeploy/test_vl/test_media_order.py tests/test_lmdeploy/test_vl/test_media_order_known_gaps.py -q
```

2026-10-21 的归档验证结果为 **612 passed、8 xfailed**。这不是全部兼容性通过：8 项严格 xfail 就是尚未修复的阻塞问题。使用固定的官方模板、本地生成的图片和最小 tokenizer 词表，不需要模型权重或 GPU；HTTP 测试模拟生成。

要把已知缺陷作为真实失败显示：

```bash
python -m pytest tests/test_lmdeploy/test_vl/test_media_order_known_gaps.py --runxfail -q
```

该文件先验证原始 HF 渲染可以生成正确占位符，再要求追踪路径保持相同输出并得到正确引用。共五个自定义模板反例、三个 Omni 模态反例。修复后移除对应 xfail；严格模式的 XPASS 会提示该更新。

## 继续实现的建议顺序

1. 先以上述反例为验收约束，设计可以随最终字符串输出传播的媒体来源信息；不要只在循环执行位置增加标记。考虑赋值、拼接、宏、过滤器、索引和循环控制，或定义显式的模板/模型适配协议。
2. 确保正常渲染输出与原来的 HF 路径逐字一致。需要兼顾模板自身的丢弃/重复媒体语义；当前“每个输入恰好出现一次”是原型约束，不是已证明普遍成立的契约。
3. 在所有收集器入口明确传递引用，涵盖默认处理器、自定义 GLM 处理器及其他旧路径。不要把 InternVL 的兼容修复误认为所有旧处理器已经接入通用引用机制。
4. 对不能证明顺序的路径制定明确能力约定。不能悄悄回退到输入顺序，因为模板可能已经重排；也不能未经范围限制地让所有原本合法的普通图片请求报错。
5. 移植最新三协议测试，覆盖完整原始多轮请求、纯文本/图片工具混合、不同轮次 ID、图片像素顺序，以及真实模板中每个文字标记与图片占位符的位置。保留普通图片、损坏图片及纯文本控制组。
6. 正确性通过后再优化双次渲染、模板缓存、标记扫描和对象复制，分别测冷缓存、热缓存、媒体数量增长和请求并发。此前约 0.7 ms 的额外耗时只是局部测量，不是稳定的性能保证。
7. 最后做真实模型服务对照：既比较 HTTP/流式完成，也比较最终图片答案；为新增失败确认基线，避免把原有模型/处理器限制和原型回归混为一谈。

当前归档没有重新启动 GPU 服务，也没有为通用原型创建上游 PR。
