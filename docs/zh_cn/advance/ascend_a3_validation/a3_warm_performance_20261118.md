## 不利信号与下一步定位

Agents64-token norm的C1 TTFT和C4吞吐各7/8配对呈不利方向，必须继续定位；正式统计标签仍遵守原±5%区间规则，没有因为区间未完全超过5%就把这些变化写成通过。主测试没有删除任何慢样本。

已开始独立的历史HTTP主机/设备计时；norm诊断优先匹配64-token场景。诊断保留原await顺序，只在退出时同步收集稀疏NPU事件；事件区间包含host enqueue间隙，不是纯kernel时间，诊断吞吐不并入主统计。

部分“未证等效”的区间只向改善方向越界。例如Agents256-token C4吞吐区间[−1.85%,+10.52%]，其不利端仍在5%内；这与norm64的明确不利方向不同。该解释不改变预先规定的验收状态，也不将未证等效的行改绿。

## 正式样本的时间边界与交叉控制

**Agents norm64 的 C4 首 token 阶段。** 在八个进程对中按相同 prompt 和批次序号逐一匹配，共 64 个批次对。128 批在两个 rank 都执行四次 170-token 单请求预填充。每一批在第四个请求收到首 token 时累计恰好交付四个 token。首个请求到第四个请求收到首 token 的间隔，按每个进程对内八个批次差的中位数汇总，八对分别为 +42.1、+47.9、+92.6、+72.2、+72.5、+53.5、+51.4、−161.1 ms，配对中位为 +52.45 ms。该间隔覆盖调度、预填充与交付。最慢的反向配对和所有原始响应均保留。[逐批时间分解](evidence/a3-warm-attribution-20261118/norm-c4-paired-stages-r0.json)

**共享 decode 图的 norm 切换。** 在同一 worker 内保持 decode 图和内存池相同，仅切换预填充使用的 norm。每个 C1/C4 负载各做八组四次测量，每组包含两次相同旧实现和两次相同新实现，按 Williams 序列平衡位置及相邻顺序。每个负载 32 批逐 token 一致，decode 全部重放，无新捕获。下表的实现差为每组两次新实现均值减两次旧实现均值，再取八组中位数；同实现重复绝对差为 16 个同标签实现配对绝对差的中位数。后一列用于描述重复运行的离散程度。

| 负载 / rank | 预填充实现差 ms | 同实现预填充重复绝对差 ms | gated norm 实现差 ms |
|---|---:|---:|---:|
| C1 / 0 | −3.73 | 12.54 | +0.04 |
| C1 / 1 | −3.90 | 13.08 | +0.14 |
| C4 / 0 | +19.35 | 38.98 | +0.46 |
| C4 / 1 | +16.62 | 38.47 | +1.22 |

首次交叉控制直接记录了 linear_attn 的五个子模块。GatedDelta 是普通 Python callable，未出现在 named_modules 遍历中，因此残余项同时包含 GDN 和其它局部操作。后续一组 C4 四处理交叉实验直接计时 GatedDelta.impl.forward、六个 chunk 阶段、卷积参考函数及特定元数据读取，共四组、16 批、64 条响应，每组输出逐 token 一致。两个实验的正式命令记录了 native 环境、固定源码、CANN 9.1 和默认 CPU 集合；两个 rank 的 dlinfer 模块审计均为空。

**设备到主机的读取已实测。** 每个 C4 批次、每个 rank 命中 1080 次所观测的 NPU 主机读取。在卷积中为 120 次长度 tolist 和 240 次张量布尔判断；在 GDN 中为 600 次长度 tolist 和 120 次转 CPU。逐批相加后取中位数，两个 rank 的这些调用占用 96.06 和 121.69 ms 墙钟时间。rank1 卷积长度 tolist 的新旧差为 +50.99 ms，同实现重复绝对差为 43.12 ms；rank0 同一调用的新旧差为 −2.52 ms。调用时间包含等待上游异步任务及主机调度。该路径及外部算子快照在 norm 比较两侧相同，尚无证据证明 norm 重构使这些调用必然变慢。共享图实验中 gated norm 的直接开销及同实现的波动，也不足以单独解释正式 C4 吞吐信号。[子调用计数及逐组计时](evidence/a3-warm-attribution-20261118/agents-norm-gdn-crossover-r0-attribution.json)

**HTTP 的服务端输出与客户端窗口。** 三个正式 HTTP 矩阵中，按原始输入匹配 1368 个新旧请求对，验证 token ID 相同。分别测 AsyncEngine.generate 首尾 token 输出之间的时间，以及客户端首尾非空 SSE 之间的时间。在历史 Agents、当前 Agents 和当前 Sage 的 C1/C4 六个组合中，两个窗口的新旧差之差，逐请求取绝对值后的中位数为 0.073–0.113 ms。多数请求的窗口变化在服务端 generate 输出处已经可见；这项比较不能区分引擎计算、服务端调度和反压，也不测首 token 的绝对交付延迟。

历史 Agents C4 有一项 390.71 ms 的窗口变化残差。检查 b01、新侧、rep6，四个请求的各 128 个 token 均能与 SSE 文本逐项对应；第 118 到 119 个 token 的服务端间隔为 12.06–13.77 ms，客户端间隔为 527.98–529.77 ms。该次长间隔出现在服务端 generate 输出后的交付或观察环节，尚不能进一步区分 SSE 服务、socket 与客户端线程。它和预填充、Ray/worker 的等待分属不同测量边界。[逐请求配对](evidence/a3-warm-attribution-20261118/http-driver-sse-windows-r0.json) · [长间隔逐 token 审计](evidence/a3-warm-attribution-20261118/http-largest-window-residual-r0.json)
