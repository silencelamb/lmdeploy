# H200 动态 HTTP C4：精度与性能分别报告

更新：2026-11-18，Asia/Shanghai。按用户要求，把逐位数值一致性与独立端到端性能分开。复用已完成的充分预热实测，并重新核验全部请求的实际工作量；没有新增GPU测量或改动原始样本、精度容差和性能回退阈值。

## 精度：自重复性具体指什么

固定同一份源码、同一配置和prompt，再次发起新请求，检查生成token ID与每步完整返回top-k分数是否逐位一致。这是数值重复性，区别于耗时每次是否相同。C4指四个并发HTTP请求；每次服务端实际就绪时间、合批大小和请求行位置仍可能不同。

六个完整模型在原报告已测的匹配配置中迁移前后bitwise一致；GLM-5.3使用独立保序控制。动态非MTP HTTP C4另外记录：

| 完整模型 | 动态HTTP C4精度 | 实际资源 |
| --- | --- | --- |
| Sage-A1.5 | 两侧自重复及迁移配对的token、完整top-k分数均逐位一致 | 单H200，TP1 |
| Agents-A1 | 两侧自重复及迁移配对的token、完整top-k分数均逐位一致 | 单H200，TP1 |
| Intern-Decision-4B | 完整评分响应及分数逐位一致；不生成token | 单H200，TP1 |
| GLM-5.3-Flash | 两侧各自重复时存在token和分数差异 | 单机8×H200，TP8 |
| Intern-S2-Preview-397B-FP8 | 两侧各自重复时存在token和分数差异 | 单机8×H200，TP8 |
| GLM-5.3（保序控制） | 两侧各自重复时存在token和分数差异 | 单机8×H200，TP8 |

前三项只说明已测单卡配置通过，不能扩展为其TP8也已验证。后三项的旧 numerical_qualified=false 保留；独立性能结论不会将其数值状态改成通过。

例如本轮保存的首次同版本token重放差异，Flash基线出现在第16个输出token，Intern-S2基线出现在第1个，GLM保序基线出现在第73个。此前相同历史和两次token值均保存在补充审计中；不是只观察到最后一位分数变化。

Flash/S2已有[冻结实验](cuda_determinism_followup_20261117.md)验证局部GEMM对batch形状、S2 BF16归约对行位置的敏感性。本轮GLM已经启用deterministic=True，C4差异不能直接再归因于旧的无序selector；其具体首差算子未进一步定位。

## 性能：本轮未发现持续回退

三个配置分别完成五对全新进程AB/BA；每进程C4先预热三批，再测五批。合计30个进程、150个计时批次、600个响应、153600个输出token。全部请求均为同一输入token序列和顺序、相同checkpoint/TP/设备/cache容量，prefix关闭、graph开启、非MTP，每请求固定输出256 token，以length结束。Flash/GLM每请求输入170 token，Intern-S2为167 token。

计时外的数值捕获在测量期间已恢复原实现；选定样本无检测到的外部GPU进程重叠。性能比较针对这个HTTP请求工作负载，允许实际合批与生成内容自然变化；它不证明内部MoE路由、每步张量或调度轨迹完全相同。

逐对变化统计沿用原规则：每批TTFT/TPOT取请求均值，每进程取五批中位数，再对五对进程统计。仅当不利配对中位变化>5%、至少4/5对>5%、95%配对bootstrap区间排除0，才触发持续回退定位。三项均未触发。
