# GLM-5.3 完整 R11 的 LMDeploy 接入与 H200 实测

**完整路径在历史运行环境用新版引擎重新 prefill，三轮平均 12.35918 ms/步。** 冻结报告为 12.34909 ms，本次在同一主机重跑原研究程序为 12.34723 ms。新接口与冻结报告相差 10.1 µs（0.082%），复现了约 12.35 ms 的水平。上一次 PR 报告的 17.958 ms 对应只换 KDA 输出投影的早期示例。[原生包与运行命令](../../../examples/specialized_execution/FULL_R11.md) · [机器可读数据](../../../examples/specialized_execution/full_r11_validation.json)

## 实验对象与口径

2026-11-26，8×H200、单节点 NVSwitch、DP8/EP8/TP1、每卡 B8。LMDeploy 开发基线是 main `f3e62520` 和 SM90 MegaMoE 前置提交 `42dc6d31` 的合并。完整 R11 接管所有 routed experts，未命中计划时使用 LMDeploy 的 default MoE 后端。模型为真实 checkpoint `3f1971b7b5f7a528c9c4ef6212c8785298a8c24a`，关闭 MTP。正式运行保留原模型和全部派生权重在 HBM。最初共享节点时每卡另外被占用约 20.8 GiB，打包出现 OOM。下表采用外部任务退出后的完整八卡运行。

每次为 64 个不同 prompt 分别做 65,536-token prefill，8,192-token 分块。同一进程内恢复同一份页池、状态、cursor 和第一步输入，32 步预热后自由生成 512 步。GPU device graph 从 step start 计到 45 层、LM head、argmax、token/position/SSM 反馈和全词表记录完成。每步先取八卡 GPU body 的最大值，然后对 512 步求均值。三个独立测量轮按相同权重、精度与缓存几何执行。另用同一步图做主机连续排队 replay，单列结果。

| 512 步控制                                    | 第 1 轮 ms | 第 2 轮 ms | 第 3 轮 ms |   三轮均值 ms |
| --------------------------------------------- | ---------: | ---------: | ---------: | ------------: |
| 原 R11，冻结的历史结果                        |  12.349835 |  12.347610 |  12.349835 | **12.349093** |
| 原 R11，本次同机重跑                          |  12.347270 |  12.346541 |  12.347890 | **12.347234** |
| 完整新接口，历史运行环境重新 prefill          |  12.359357 |  12.359528 |  12.358660 | **12.359181** |
| 完整新接口，干净运行环境恢复历史 prefill 快照 |  12.365968 |  12.364267 |  12.366157 | **12.365464** |
| 完整新接口，干净运行环境重新 prefill          |  12.391818 |  12.387810 |  12.387197 | **12.388941** |

历史环境中新版默认路径为 18.00738 ms，完整 R11 降低约 31.4%。同一组数据中，完整 R11 主机预排队回放为 12.36489 ms。干净环境从源重新编译原生包，恢复历史 prefill 后另测三轮 12.36661 ms。原版与新接口的冻结轨迹捕获图在每个 rank 的 kernel 标签顺序及依赖边逐项相同，共 1,273 个节点、1,265 个 kernel 标签、1,455 条边。图中每步有 34 个融合 KDA 递推、34 个 R11 输出投影、42 个 packet planner、42 个 132-CTA expert grid、11 个 KPool Top-K 和 90 个 mHC post。剩余约十微秒的差距未单独归因。 [同口径驱动](../../../examples/specialized_execution/benchmark_full_r11.py)

## 数值一致性与状态回退

- **冻结轨迹。** 新版引擎在历史环境重新 prefill 后，普通和完整 R11 路径都复现了归档的 32,768 个生成 token。每轮比较 512 步原生 BF16 全词表的字节摘要、四类语义状态以及五个完整物理缓冲或游标，八个 rank 全部匹配。全词表覆盖每请求的全部 154,880 项。
- **新环境。** 新环境独立 prefill 时，64 个 prompt 的第一个预测有 32 个与历史环境一致。两个环境的 prefill 池已经不同，直接比较此后 512 步自由生成会混合 prefill 和 decode 的影响。在新环境用同一份快照分别跑普通与 R11 路径，全词表、状态和物理池仍完全匹配。加载历史真实快照后两条路径都恢复旧 token 轨迹。将相同的旧 prefill 源码分别放入新旧环境，rank 0 的 8K 分块探针也观测到差异。旧源码和新源码在同一新环境采得的 375 组样本逐项相等。探针只定位了数值分叉的阶段。
- **Cursor。** 首轮两个独立进程的比较在两个 rank 的第 5 个缓冲出现差异。两种摘要对应保留槽 0 初值为 0 或 −1，其余八个 cursor ID 都是 1 至 8。验证驱动现在让 forward stream 等待 cache 构造 stream，再初始化池。对照从相同状态恢复，保留槽也计入验收。
- **动态回退。** 输入页交错、state slot 反向，行顺序交替变化，初始 KV 长度分别取 65,536/65,537/65,538。第 3 步只有 rank 0 缩至 B7，所有 rank 走普通图，随后全部返回 R11。五步整词表及全部五个最终缓冲逐字节相等。单个真实 HTTP 请求也覆盖其他 rank 为 dummy 的情况。启动 warmup 由八个 rank 对称地使用保留槽。实测普通图与 R11 专用图均在 startup 捕获，真实请求复用图缓存。 [动态测试](../../../examples/specialized_execution/check_glm53.py)

## 实际 Serving 步时

使用真正的 `lmdeploy serve api_server`、八个 Ray worker、八个 HTTP 端点与 `/generate` 流式客户端。每个端点提交八条 64K 输入，每条收满 512 个输出 token，每轮总计 4,194,304 个输入和 32,768 个输出。时间戳版本在专用 forward 的首尾各放一个设备节点，干净测量轮关闭 CUPTI。计算相邻真实命中步的 start-to-start，每步取八卡最长区间，并在同一张卡上分解为 body 和步间间隔。稳态表固定去掉头尾各 8 个区间。未裁剪结果也保存在 JSON 中。

| 部署 / 测量                                                | 均值 ms | p50 ms | p95 ms |
| ---------------------------------------------------------- | ------: | -----: | -----: |
| 两个 GPU 时间戳，首个真实 B8 按需捕获，稳态 start-to-start |  13.160 | 13.150 | 13.316 |
| 同组区间的 R11 forward                                     |  12.741 | 12.758 | 12.923 |
| 同组区间的 forward 结束至下一步开始                        |   0.419 |  0.393 |  0.401 |

首次按需捕获约用 7.8 s。该对照的每请求 TPOT p50 为 94.27 ms，流式单 token 到达间隔 p50 为 13.14 ms。前几个请求出首 token 时，其余长 prompt 仍在 prefill。请求级 TPOT 会计入穿插的重 prefill 和首次 capture。最终 provider 通过全组 dummy 启动预捕获测试后，已将两条图的捕获放进正常 warmup。直接客户端与最终 warmup 配置的结果见下表。

## 差距在哪

rank 0 的 CUPTI 诊断窗口与干净计时轮分别采集。固定控制在 48 个真实 decode 更新后，连续从 host 预排队回放同一整步图，分析 30 个完整区间。HTTP 使用单独的诊断流量，分析 26 个完整 R11 区间。二者每步都执行相同数量的 R11 子程序。

| rank 0 每步的 CUDA 观测           | 固定窗口 ms | Serving 窗口 ms |    变化 ms |
| --------------------------------- | ----------: | --------------: | ---------: |
| 42 个 routed expert grid 耗时合计 |       4.357 |           5.182 | **+0.825** |
| 42 个 packet planner 合计         |       0.411 |           0.372 |     −0.039 |
| 34 个 R11 KDA 输出投影合计        |       0.782 |           0.784 |     +0.002 |
| 11 个 sparse MLA 主核合计         |       0.518 |           0.514 |     −0.004 |

42 层的 routed grid 各自都变慢，每层增加约 12.0–31.5 µs，中位数 18.9 µs。独立路由探针读取实际 planner 的每卡 54 个物理专家计数，每层跨卡合计恰为 `64×8=512` 个路由槽。逐层取负载最重的 rank，再跨层求和，一个专家计 `3×4096×2048` 个 FP8 权重字节。稳态唯一专家权重载荷由 **19.007 增至 22.866 GB/步（+20.3%）**，考虑 M32 重复 tile 后由 **19.500 增至 22.881 GB/步**。异步准入与实际生成轨迹改变了同时执行的专家集合。这些字节是逻辑载荷估算，实际 HBM 交易还受 L2 命中影响。诊断核耗时可跨 stream 重叠，不能把各核之和直接加到端到端时间上。

在同一 Serving trace 中，forward 之外的平均间隔为 0.426 ms，其中 GPU 活动并集占 0.346 ms。LM head GEMM 约 0.300 ms，其余包括归约、状态/索引和拷贝。没有观察到 CUDA 活动的剩余部分约 0.080 ms。这些是重叠后的暴露时间，不能用所有 CPU 等待事件的总时长代替。固定 12.35 ms 的计时本来就包含 LM head。 [Trace 与路由统计脚本](../../../examples/specialized_execution/analyze_full_r11.py)

## MTP 的接口边界

`FullR11` 只声明 AR target 的 B8/q1。框架会在初始化时排除 MTP，当前 KDA 核也要求 `output_state_ids.shape == (8,1)`。若生成团队提供 MTP 版 R11，模型 forward 边界、权重准备、EP 组一致选择和图重放仍可复用。接口需把 target verify 与 draft 分开建计划，加入每行 query 宽度、有效候选和 padding、所需 hidden/embedding 输出，以及拒绝采样后由引擎执行的 accepted-prefix 提交/丢弃。KDA 递推、卷积、KPool tail、cursor 和 KV 可见长度均要与接受边界对齐。EP8 的 packet/返回区也必须按实际 token 行数重新生成。V1 当前没有 MTP 验收结果。

本地回归为 686 通过、1 项因缺少真实昇腾运行时跳过。原始逐卡时间戳、整词表哈希、全池哈希、两份图及 GPU 时间线均可下载复算。[压缩验证证据](https://github.com/silencelamb/lmdeploy/blob/43228c050b6758a11cf5cfc5d97c7b1d8e789797/glm53-r11-h200-validation.tar.gz)
