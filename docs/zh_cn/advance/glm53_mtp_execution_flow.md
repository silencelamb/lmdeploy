# GLM-5.3-Flash 的 MTP3：谁预测、谁验证、谁提交

## 哪些能力原来就有

LMDeploy 在 `b31a0a49`（#4968）已接入 GLM-5.3-Flash 及其 MTP predictor。本次使用的真实 checkpoint `3f1971b7` 有 45 个主干层和 1 个 NextN 预测层。**目标模型始终是 GLM-5.3-Flash**。`deepseek_mtp` 是 LMDeploy 共用的 proposer 策略名。GLM 的 `Glm5NextMTPModel.load_weights` 从同一份 checkpoint 加载预测层，proposer 绑定目标模型的 embedding。MTP3 表示复用预测层连续提出 3 个候选。[GLM 接入提交](https://github.com/InternLM/lmdeploy/commit/b31a0a4985012feeb3db83f0489199bf21558fdb) · [GLM predictor](../../../lmdeploy/pytorch/models/glm5_next.py) · [共用 proposer](../../../lmdeploy/pytorch/spec_decode/proposers/deepseek_mtp.py)

**本轮 #5195 新增了 target verify 的专用执行入口，并在 8×H200 上实测。** GLM 的 45 层都参与前向；当前的 MTP3 示例在 B2×Q4 条件下，用 R11 原生核替换其中 34 个 KDA 层的输出投影。其他算子、NextN 预测、LM head、采样和提交沿用原实现。Eager 和 CUDA Graph 都用相同 prefill 快照覆盖接受 0/1/2/3 个草稿的情况，对齐全词表 logits、候选与提交状态，以及全组动态回退后的下一步。真实 HTTP 走原生 proposer；额外的同输入投影检查覆盖 204,996,608 个 BF16 元素。不同进程独立运行时的整段 token 一致性仍未通过，原生对原生也有分叉。12.341 ms/步是完整 R11 在 B8×Q1、64K、512 步普通 AR 中的成绩。完整 R11 在 B8×Q4、32 个输入位置的 MTP3 verify 尚未实现。[工作样例](../../../examples/specialized_execution/glm53_r11.py) · [数值验证、限制与逐项记录](glm53_specialized_mtp_deployment.md)

## 一轮实际怎么走

| 阶段           | 此时计算什么                                                                                                                                                                                                                                                         | #5195 中的归属                                                                                                                             |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 接入和 prefill | 收请求、选 batch、恢复前缀或运行 prompt，分配 KV 页和辅助状态槽。取得首个已确定 token 和供预测使用的目标隐藏态。                                                                                                                                                     | LMDeploy 调度器与原生 prefill。                                                                                                            |
| Draft          | 用上轮保留位置的隐藏态和 token 等输入，运行 GLM 自身 NextN 预测层，依次提出 `d1,d2,d3`。draft 的 cache 和执行上下文独立管理。                                                                                                                                        | LMDeploy 编排 GLM predictor 的模型计算。                                                                                                   |
| Target verify  | 对每条请求打包 `[x,d1,d2,d3]`。主模型读已提交前缀，一次因果前向得到四个位置的 hidden；LM head 给出四份下一个 token 分布。第一份检验 d1，第二份检验 d2，第三份检验 d3，第四份给出全接受时的 bonus。每个位置的 recurrent/卷积/KPool 状态和分页 KV 按引擎给定的槽写入。 | 八个 rank 协商是否启用生成的 target 计算。命中后执行 provider；普通与专用 forward 返回同样的 hidden 及所需辅助输出。LM head 仍由引擎调用。 |
| 接受与提交     | 贪心模式逐个核对 target 的首选 token；随机采样走已有的拒绝/恢复采样路径。按请求保留连续匹配的前缀，在第一个拒绝处用目标模型的 token 补上。逻辑长度与辅助状态 cursor 只前移实际消费的位置；到 EOS/长度上限时按请求停止。                                              | LMDeploy 的 rejection sampler、cursor 和 scheduler；流式输出与下一轮组批也在引擎。                                                         |

`x` 是已经确定、正在送入主模型的 token。如果候选是 `[A,B,C]`，主模型的贪心预测先后是 `A,X`，本轮发布 `A,X`。主模型状态提交到输入 `[x,A]` 之后，`X` 是下轮的起始输入。若三个全中，本轮发布 `A,B,C` 和一个 bonus，状态提交到 `[x,A,B,C]` 之后。因此只存四个位置的最后一份 KDA 状态无法支持部分接受。这里的一次因果前向可将投影等计算跨位置打包，递推自身仍要遵守同一请求的位置顺序。[采样与下一轮 draft](../../../lmdeploy/pytorch/spec_decode/spec_agent.py) · [拒绝采样](../../../lmdeploy/pytorch/spec_decode/reject_sampler.py) · [逻辑长度](../../../lmdeploy/pytorch/model_inputs.py) · [状态槽选择](../../../lmdeploy/pytorch/compact_state.py)

对 H200 版本，适合保留一个明确的所有者来决定可发布的 token 和可见的状态前缀，同时允许后续把 draft forward 或跨阶段的设备计算专用化。优先级应由真实 C70 的分段时间和各 rank 同时命中的 B/Q 决定。可直接借鉴的优化是同一请求的四个 verify 位置共享历史页和索引 key，仍按各自行的 query 与可见池边界打分。AMD 的 #100 就把索引任务从逐行读同一 tile 改为一次读取供四行使用；H200 的收益需要在本机测量。[同一请求的索引读取复用](https://github.com/sgl-project/sgl-amd-mono/pull/100)

## C70 的每 token 时间

`c70-r3` 的启动日志确认了 DeepGEMM MegaMoE（融合 shared expert）和 **FlashKDA prefill**，MTP 深度为 3。8×H200、DP8/EP8、Mooncake、Weka 256K、seed 20260707。正式窗有 2,307 条请求，2,364,812 个输出 token，去除每条首 token 后共 2,362,505 个间隔。用同一批逐请求数据重算：[配置与基准结果](https://github.com/silencelamb/lmdeploy/blob/d16aabc6fef030419745db1cb5d7d4204a64e735/benchmark/glm53_mega_moe/results/qa_agentx_mtp3_mooncake.json) · [聚合输入和结果](../../../examples/specialized_execution/mtp_main_validation.json)

| 项目                     |               正式窗结果 | 如何计算                                                                   |
| ------------------------ | -----------------------: | -------------------------------------------------------------------------- |
| 按 token 间隔加权的 TPOT |      **16.617 ms/token** | 各请求从首 token 到结束的时间总和 39,257,912.245 ms，除以 2,362,505 个间隔 |
| 各请求 TPOT 算术平均     |          20.141 ms/token | 先对每个请求计算 TPOT，再对 2,307 条请求等权平均                           |
| 各请求 TPOT 中位数 / p95 | 15.189 / 47.566 ms/token | 对同一批逐请求 TPOT 取分位数                                               |

QA CSV 分别将前两项命名为 `TPOT_aggregate(ms)` 和 `TPOT_mean(ms)`。16.617 是这次历史回放的实际聚合值，后续配置的 C70 成绩需要对应的正式窗记录。GPU 的固定形状单步时间另行计量。
