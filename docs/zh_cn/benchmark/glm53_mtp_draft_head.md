# GLM-5.3-Flash 在 H200 上的 MTP 草稿投影

在原调度的同服务配对中，每 rank 四条在途请求时，词表分片使 MTP3 每请求每实际输出 token 的计算流时间从 4.956 降至 4.767 ms。`LMDEPLOY_GLM53_DP_DRAFT_HEAD=1` 开启分片，默认值为 0。各轮测量、启动配置和原始 run 索引见[机器可读结果](../../../benchmark/glm53_mega_moe/results/h200_mtp_draft_head.json)。

AgentX C90 中，在对齐调度上开启分片，输出吞吐 +2.20%，goodput +3.26%，TTFT p95 降低 139 ms，TPOT p95 增加 1.12 ms。原调度上单独开启时，吞吐变化为 +0.16%。本轮最高 goodput 来自两者同开，最低 TPOT p95 来自仅调度。

## 词表投影

MTP3 的目标模型每轮验证最多四个位置，再串行提出三个草稿 token。每次草稿投影使用目标模型的 154,880 × 4,096 BF16 权重。原路径的每个 rank 每次投影都读取约 1.18 GiB。MTP5 每轮要做五次投影。

首个草稿用 `DPMeta.dp_batches`，随后的单位置草稿用 `DPMeta.dp_token_counts` 确定全机最大行数。每个 rank 将隐藏状态补齐，经现有 EP 组 all-gather，取已有权重中属于本 rank 的 19,360 行视图，为所有请求计算该词表分片。all-to-all 把分片送回请求所属 rank，按词表顺序拼接并裁去补齐行。均衡时设每 rank 有 B 条请求、词表大小为 V。乘法从 [B, 4096] × [4096, V] 变为 [8B, 4096] × [4096, V/8]，乘加总数相同，单次权重读取服务更多行。批次不均衡时还要计算补齐行。语法掩码和 argmax 继续使用本地请求的完整 logits。每 rank 每次投影的权重读量按张量尺寸计算为 151.25 MiB。B4 时每 rank 的 all-gather 结果为 256 KiB，all-to-all 的发送张量约 1.18 MiB，两者都包含本地份额。

分片条件为 GLM 的 DeepGEMM MegaMoE、DP8/EP8/TP1、全局解码、最大请求行数 1–16，以及可八等分的无偏置 BF16 词表。其余形状、全局 prefill、确定性模式和不同 head 精度使用已有本地投影。后续 AR 草稿按各自的全局元数据判断。每次调用都取当前权重。16 是本次启用并验证的上限，17 和 32 行另测本地回退。[DeepseekMTP 实现](../../../lmdeploy/pytorch/spec_decode/proposers/deepseek_mtp.py)

仅测真实词表权重，B4 的投影含集合通信从 303.1 降至 115.7 µs。每次循环 60 次，交替开关八段，先在相同测量段取八个 rank 的最大值，再对同一开关取中位数。完整一轮还包含目标前向、三个草稿的其他算子及 rank 间等待。

贪心窗内 42 个目标 MegaMoE 主核合计 7.30 ms/轮，三个单层草稿前向区间的核时分别为 0.508 / 0.357 / 0.364 ms，前向后的三次词表 GEMM 另占 0.89 ms，约为整个草稿阶段核时的 41%。若其他计算和等待完全不变，消去三次 GEMM 可回收的核时上限为 0.89 ms/轮。真实分片仍需矩阵乘与通信，整轮收益实测见下表。随机采样窗观察到接受 0、1、2、3 个草稿的全部情形。两个窗的输出轨迹和路由不同。

## 独立执行开关

同一服务固定原调度，轮换四个种子和“词表分片 × Gloo 后台等待”四种组合。下表在原有 Gloo 等待路径上比较词表分片的开关。每个种子生成 B 条 1K prompt，同一编号的 prompt 在八个 worker 上各发一次，先预热本地前缀，再固定生成 512 个 token。八个 rank 从同一集体轮号取得开关，用计算流上的 CUDA event 和逐行输出 ID 记录阶段边界与接受量。每个稳态样本取同一轮所有 rank 中最大的起止 event 区间，其中包含流上的等待。每请求成本用这些区间之和乘以全机活跃请求数，再除以实际提交的 token 总数。

按全机交付量分摊，B4 的最慢 rank 计算流时间为 0.1549 → 0.1490 ms/输出 token。该口径只取八个 rank 都在生成的集体轮。B4 的四个种子均缩短整轮时间，分别节省 0.723、1.284、0.717 和 0.397 ms。

客户端再限定到所有请求都处于第 32–480 个 token 的时段，按相同请求、相同输出前缀及相同提交边界配对。每 rank 有 1、4、8 条请求时，分别保留 3,508、9,848、15,592 个请求轮。每 token 的配对流式间隔为 3.823 → 3.796 ms、5.010 → 4.827 ms、5.959 → 5.824 ms。完整 512-token 输出逐项相同的请求分别为 32/32、103/128、178/256。

相同输入在两次关闭分片的独立冷启动中，B4 有 60/96 条完整输出逐 token 相同。服务层的自由生成存在运行间差异，配对统计按实际一致的前缀取数。

## MTP0、MTP5 与正确性

MTP0 用 1K context、一个真实 rank 加七个 dummy rank，在同一 forced-token 轨迹上跑两轮 64 步。rank 0 每步分别为 10.865 / 10.818 ms。另采 16 个 profile 步，CUDA 核区间并集 9.704 ms/步，稠密矩阵乘 4.40、MegaMoE 2.02、mHC 1.23、MLA/Indexer 0.68 ms/步。全机服务中每 rank 一条、四条真实请求时的 MTP0 成本分别为 11.197 / 13.965 ms/token。

真实 checkpoint 的八卡逐列输入检查通过。启用分片的 6,516 行随机输入 top-1 匹配 6,516，完整 logits 最大绝对差为 0。检查覆盖本地空行、不同 rank 行数、两种草稿元数据和超过 16 行的回退。调度及执行同开时，16 条 64K passkey 全部命中，32 条在途流完整返回。另一次跨 worker 恢复命中 65,472 个外部缓存 token，冷读、恢复读均答对。16 条有语法约束与 16 条普通请求同时通过。去掉每个流的首尾块，随机采样时 MTP3 的 1–4 个、MTP5 的 1–6 个提交长度均实见，覆盖零、部分和全部草稿接受。

发布代码回归覆盖 FlashKDA、compact KDA/KPool、部分与零接受、语法约束和 MTP 状态恢复。CPU 套件结果为 `126 passed, 1 skipped, 14 warnings in 8.32s`，GPU 套件结果为 `369 passed, 15 warnings in 407.20s (0:06:47)`。

## 消融和复现

缩小验证 MoE 的 BLOCK_M 在八 rank、三个 MTP 深度、五个 batch 上通过逐值检查，原调度 B4 同轨迹成本从 4.915 升至 5.024 ms/token。后台线程等待 Gloo 缩短了独立 CPU 探针的等待，实服收益随并发和负载变化。合并 top-p 过滤的实验在 12,312 个 bonus 行中改变了 22 行有效分布，固定随机种子的对照中有 12 个 bonus ID 发生变化。三项消融的提交及原始路径都在结果 JSON 中。

首次四格补充恢复探针把整数 token 列表传给了 completions 入口。第二次运行用原生 `/generate` 得到八次正确答案，跨 worker 命中计数在请求完成后才更新。选入表格的完整重跑先建立写入后的计数基线，再等目标读取反映在监控中。

服务端设置 `LMDEPLOY_GLM53_FLASHKDA_LIBRARY` 指向 SM90 扩展，使用 `LMDEPLOY_GLM53_DEEPGEMM_FUSE_SHARED=1` 和交错 FC1 布局。算子复现读取真实词表权重，流式客户端直接请求八个 worker。

```bash
torchrun --nproc-per-node=8 benchmark/glm53_mega_moe/bench_mtp_draft_head.py --model "$MODEL_SNAPSHOT" --output "$NEW_MICRO_DIR"

python benchmark/glm53_mega_moe/mtp_execution.py --urls "${WORKER_URLS[@]}" --monitor-port 23710 --tokenizer "$MODEL_SNAPSHOT" --draft-depth 3 --batch-per-rank 1 4 --repeats 3 --output "$NEW_RUN_DIR"
```
